让 AI 回答一次问题，如今已经不算难。想让它每天按约定整理一份报告，事情立刻多起来：什么时候运行，依据哪一版规则，读到的数据是什么时点，结果少一节怎么办，生成以后又怎样送到手里？

笔者做 Daywise（日有所见），起点就是一个很普通的想法：让 AI 每天帮忙看看，整理出便于阅读和复核的研究材料。后来逐步发现，回答本身只是其中一段。定时触发、输入管理、输出校验、排版与投递，每一段都得有人负责。

项目辅助研究和阅读，不登录券商，也不执行真实交易。这里想留下的是把它做成日常工具的过程，不展示个人账户、研究参数或收益。

## 先看整条管线

目前采用的分工是：GitHub Actions 负责定时或手动启动任务，Codex 负责检索与结构化分析，Python 程序负责验证结果、渲染模板和封装邮件。

GitHub 保存版本化代码，云端开发环境提供修改和检查代码的条件，Actions runner 则执行日常任务。三者分工清楚以后，日常运行不要求个人电脑开着，也不要求维护项目的聊天一直在线。

模型最终写出一份结构化分析，程序再生成完整 HTML 报告，并派生邮件摘要、图表数据和 Actions 阅读版。不同日期可以安排不同章节，但附件仍保持一份，避免主题多了，收件箱里也跟着多出一排文件。

## 先让失败发生在哪里变得可见

最初关注的是调用能否完成，后来陆续补上显式认证、运行日期、失败诊断和产物保留。

其中一个很小却很要紧的细节，是“今天”到底指哪一天。提示词里写今天，人看着明白，程序却还需要一个明确日期。报告日期、章节计划和校验规则必须使用同一个口径，否则跨时区运行时，一份看起来完整的报告也可能选错章节。

早期还遇到过沙箱写入兼容性问题。处理办法包括选择合适的运行镜像，以及在调用模型之前先做小规模写入检查。结果如果落不了盘，最好在付费调用前发现，而不是等分析结束以后再研究文件去了哪里。

这类预检不能保证任务永远成功，但能尽早排除一部分配置问题。也没有必要为了跑通一次任务，就把安全隔离关掉。

## 定时任务的时间，得拆开看

另一件容易误会的事，是把计划触发时间当成实际开始时间。

排查调度延迟时，需要至少区分三个时刻：预定的运行时刻、GitHub 创建这次 workflow run 的时刻，以及 job 真正开始执行的时刻。等在哪里，要看这段时间线，不能只看 cron 写得是否正确。

项目历史里尝试过提前调度和调整运行日期范围，后来回到显式时区下的工作日安排，并保留诊断记录。单纯把 cron 提前一些，不能证明平台调度延迟就此消失。

目前也不能承诺准点。如果某件事必须在精确时刻完成，就需要另外评估调度保障；不能因为连续几次按时收到报告，就把偶然顺利当成服务保证。GitHub 的[定时事件文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)可供进一步查阅。

## 提示词长起来以后，先拆输入

刚开始，把要求放进一大段提示词很方便。后来信息越来越多，就得分清哪些是长期规则，哪些只是今天的看法。

Daywise 逐步把输入拆成几个部分：调度配置决定何时运行，章节计划决定这次写什么；策略规则保存相对稳定的约束，已确认状态保存某个时点的事实；临时观察和研究提示另行维护；输出契约与展示模板则约束结果怎样落地。

这里最有价值的边界，是不同信息不能互相冒充。

临时观察不会自动改变机械规则，文件导入日期也不等于数据确认日期。历史状态可以作为分析背景，但不能因为今天读了它，就称其为实时账户信息。日常报告读取确认过的状态，不自动覆盖原始快照。

这些约束听起来不像 AI 功能，却会直接影响后续维护。否则改一段观点，可能顺带改了规则；更新一份报告，又可能把未经确认的内容写回事实。工具越自动，这种混淆越不容易在当时被注意到。

## 一份结构化内容，多种阅读方式

当前流程要求模型写出一份结构化分析文件。Python 程序按照计划检查日期、必需章节、表格和来源字段，再交给模板生成展示内容。

这样，模型不用分别写一份长报告、一份邮件摘要和一套图表说明，减少了几种版本互相打架的机会。报告保留章节导航、表格和来源，邮件正文则用短摘要与可视化卡片帮助快速阅读，详细内容放在 HTML 附件里。

结构化结果也不能直接当作任意 HTML 塞进页面。普通文本需要转义，并与受信任的模板片段区分处理。现有测试覆盖了 HTML 注入、缺失占位值、非法路径和异常文件名等情况。Python 标准库中的 [`html.escape`](https://docs.python.org/3/library/html.html#html.escape)提供了文本转义的基础能力，但具体哪些内容允许进入哪个位置，仍由程序和模板负责。

这里的“校验通过”只表示结构与一致性满足程序要求。来源字段写全了，不证明来源真的支持结论；日期格式正确，也不证明行情仍然有效。更深入的来源一致性和时效检查，仍有继续完善的空间。

## 图表别替未知数据装作精确

邮件里加图表，是为了减少阅读时反复换算和判断的负担。不同指标的方向尽量统一，颜色和模板也独立维护。

但图画得漂亮，有时反而容易掩盖信息缺口。因此，已知、部分未知和完全未知的数据，需要使用不同表达。无法确认的值，不放一个看似精确的游标；只有部分信息时，可以表达范围，而非补出一个恰到好处的小数。

这些图表帮助复核条件，不是收益预测，也不是下单指令。读者应该能看出哪里有数据，哪里还需要确认。没有信息的地方，留白比画得很有信心更有用。

## 报告生成了，邮件还得另算一笔账

有了文件，还得把它交给阅读者。项目增加了 Actions Summary 和邮件投递，SMTP 使用 TLS 或 STARTTLS，凭证通过运行配置提供，不写进代码。

多收件人采用分别投递，避免把地址列表暴露给其他收件人。报告生成和邮件发送也分开处理：发送失败时，保留已经生成的报告，不能靠重新跑一轮模型来掩盖投递问题。

此外，SMTP 服务器接受消息，只能说明它接受了这封邮件，不能证明邮件已经进入收件箱。真实收件要单独确认。Python 的 [`smtplib`](https://docs.python.org/3/library/smtplib.html)负责邮件协议交互，无法替人担保后续每一个投递环节。

## 到底验证到了哪一步

整理本次交接材料时，Daywise 一侧重新运行了配置检查和测试：

```sh
python3 scripts/check_configuration.py
python3 -m unittest discover -s scripts -p 'test_*.py' -q
```

交接记录显示，42 项测试全部通过，覆盖模板安全、章节与日期校验、策略配置变化、可视化缺失值、多收件人邮件和 TLS 等。当前 Python 管线使用标准库，没有额外第三方 Python 依赖。

这些是素材制作时记录的本地验证结果。测试里的 SMTP 是模拟行为，没有真实发送邮件；本次也没有触发付费模型调用或生产 Actions。

早期版本有真实模型运行和邮件收件的文档记载，但这次交接没有重新查验对应远端证据。新版采用单份结构化输入和单附件，本地测试已通过，现有材料中的首次真实模型运行完整验证仍待完成。早期版本成功过，不能直接替新版签收。

因此，目前能说明的是：若干程序边界和错误处理已有测试覆盖。还不能据此宣布报告内容准确、判断有效、调度准点或邮件必达。后续可以继续补来源与时效检查、跨日报告对比、漏跑检测、投递去重，以及只补发邮件的入口；这些仍是改进方向。

## 项目经验也需要一条交接管线

最后，Daywise 还多了一种产物：可以公开的工程经验。

这篇文章的素材先在 Daywise 中整理，删去私人信息，形成独立可理解的交接包；配图放到静态资源仓库，清单固定图片提交、哈希和使用依据。再由我明确要求博客项目接收指定版本，按既有写作和发布流程处理。

两个对话不必共享完整聊天。文件保存经过选择和复核的知识，Git 提交固定版本；两次指令分别控制素材交接和博客发布。接收方仍要再次检查隐私，不能因为目录叫 ready，就直接原样公开。

共享私有仓库的环境，技术上可能读到整个仓库。目录约定是日常操作边界，严格权限隔离仍需要独立素材仓库。本文只使用指定交接材料，没有从私人数据或原始日志补写背景。

做完这些，越来越觉得，一个日常 AI 工具的可维护性，藏在那些不太像 AI 的部分里：输入能否追溯，未知是否如实表达，失败后有没有证据，交付能不能单独检查。

先把这些事情安排好，再继续扩展模型能做什么。这样，明天需要改一点东西的时候，至少知道该从哪里下手。
