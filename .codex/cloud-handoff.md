## 项目与协作范围

- MyNote 是作者的个人 Hugo / PaperMod 博客，网站为 https://guyuechen.icu。
- 当前 GitHub 仓库为 `uytrdcvbjhgf/guyuechen.github.io`，发布分支为 `main`。本地 origin 可能仍使用旧地址 `guyuechen/guyuechen.github.io`，不要据此创建新仓库或自行更换远端。
- 日常任务是通过聊天收集想法、整理或修改 Markdown、验证结果，再按用户要求提交和发布。
- 主要修改范围为 `content/posts/`。主题、布局、资源、部署和站点结构的修改须有用户明确要求。
- 原本混在本地聊天中的每日投研报告已迁往另一个云端任务，本地定时任务已由用户暂停。博客云端环境不承接这些定时报告，不创建同类任务。
- 此文档只保存可公开的博客协作知识。账户、持仓、健康资料、密钥、私人素材及完整聊天记录不属于交接内容。

## 补充写作偏好

- 默认中文，修改集中于用户指出的地方，保留原意和个人经历。
- 随笔通常放在 `content/posts/others/`；近期随笔使用 `categories = ['diary']`、`tags = ['diary']`，新任务按用户要求及 taxonomy 决定。
- 随笔标题简短，语言精炼，可有口语、冷幽默和个人思考。减少反复出现的主语，按节奏使用“笔者”或“我”。
- 技术科普要结合本仓库代码和实际结果，讲清触发条件、机制及限制，区分事实、推测和待确认项。
- 月份、年数等计数可采用 `11 月`、`5 年、10 年` 的写法；不要机械替换成语、引用或固定名称里的中文数字。
- `a-year-with-ai.md` 和 `blog-quality-hooks-and-actions.md` 是可参考的近期文章。引用它们的经历或结论前，应读实际内容。
- 使用 `+++` TOML front matter，遵守仓库的字段与单引号风格。已发表文章的首次发布日期保持不变；草稿修改和首次发布按既有规则更新时间，默认时区 Asia/Tokyo。
- 用户在聊天中同意文章措辞，不自动等于要求立刻发布。执行提交、推送、开 PR 或合入时，结合当前任务的明确授权；不要在每个已经授权的步骤重复询问。

## 云端环境要求

建议建立名为 `MyNote` 的独立 Codex Cloud 环境，只选择本博客仓库。

- Node.js：24，与仓库 Actions 一致；具体最低版本看 `package.json`。
- Hugo：Extended 0.133.0，与当前部署 workflow 一致；若仓库版本已更新，以代码为准。
- 递归初始化 `themes/PaperMod` 等 Git 子模块，使用仓库记录的提交，不更新到上游最新版本。
- 安装依赖时使用 `package-lock.json`，不为迁移随意升级依赖或重写锁文件。
- 根据配置和构建日志补齐确实需要的 Sass 等工具；以完整构建通过为验收标准。
- 网络需满足仓库及子模块读取、依赖下载、工具安装、GitHub API 访问；写文章需查资料时还需对应资料源访问。允许联网与拥有仓库写入权限是两回事，分别核对。
- 不需要为现有规则式文章校对配置 OpenAI API key。
- 新 checkout 不继承本机 Git 配置和登录。检查 `core.hooksPath` 与 GitHub 身份，按云端提供的连接方式配置；不要将凭据写入仓库或聊天。

## 检查、校对和发布机制

- `.githooks/pre-commit` 在提交前运行 `node scripts/article-quality.mjs staged`。完整暂存的文章可自动修格式并重新暂存；部分暂存的文章会拒绝提交。
- `npm ci` 的 prepare 会尝试安装仓库本地 hook，但 `scripts/install-hooks.mjs` 在 CI 环境跳过安装，也会保留已有的其他 hooksPath。云端不能只因依赖安装成功就声称钩子已启用。
- 若钩子尚未安装，先检查已有配置；在没有其他钩子冲突时，将当前 checkout 的 `core.hooksPath` 配置为 `.githooks` 并复查。不要覆盖其他钩子，也不要修改全局 Git 配置。
- 即使钩子已安装，提交前仍检查实际 diff 和必要的格式结果。不要通过跳过 hook 来掩盖普通文章问题。
- `Article checks` 检查格式与脚本测试，不创建修正分支或 PR。
- `Article proofreading` 在 runner 中生成建议和中文词典修正候选，通过独立 bot PR 供作者检阅；英文拼写建议保留在报告中。它不是 AI 语义校对，也不会自动合入。
- `main` push 会触发部署 workflow，内部先检查再构建 Hugo。只提交文档也可能触发检查和部署；是否触发校对取决于它的路径过滤。
- 不同 workflow 的触发器独立。bot PR 的 Actions 可能需要维护者批准运行；“允许 workflow 运行”“检查通过”“认可改文”“合入 PR”分别判断。
- 运行历史、PR 编号和权限状态会变化。历史例子见文章；当前结果要重新读取，不能把过去的成功记录当成本次通过。

## 云端首次验收

1. 确认当前仓库、分支、工作目录和 `git status`。Linux 云端使用实际路径，不使用 `C:/note/blog`。
2. 读取交接规则，初始化子模块，安装固定版本工具和依赖，确认 hook 配置。
3. 运行 `npm test`。选择相关现有文章显式运行 `npm run articles:check -- content/posts/others/blog-quality-hooks-and-actions.md`，不要仅依赖“没有变更文件”的跳过结果。
4. 使用与项目配置相容的生产参数运行 Hugo 构建，验证主题和所需资源工具。将构建产物视为产物，不擅自提交。
5. 核对 GitHub 连接是否能读取仓库、推送分支及创建 PR。未实际进行写入测试的能力应明确标为未验证；没有测试分支或 PR 的授权时，先只读检查。
6. 回报工具版本、测试和构建结果、hook 状态、GitHub 权限确认程度，以及缺少的用户操作。验收不要求修改文章或发布新内容。

默认建议的后续协作方式为：云端编辑和检查 → 推送工作分支并开 PR → 用户检阅合入 → 现有 Actions 发布。此为迁移建议；用户可明确要求直接推送已有工作流允许的分支。

## 跨设备与后续维护

- 需要继续未完成工作时，回到同一个云端聊天。新聊天有独立工作目录，不会自动取得另一个聊天的未提交草稿。
- 重要稿件及时提交并同步到远端的工作分支；不要只依赖聊天上下文或云端 VM 的保存状态。
- 开始新工作前先检查工作区再同步远端。合入 PR 后，本地主分支无未提交改动且未分叉时，可用 `git pull --ff-only origin main`；有改动或分叉时先处理它们，不强制重置。
- 云端环境配置属于环境的可复用起点，Git 仓库保存项目与文章；聊天承担当次交流。更新环境、代码和写作偏好时，各自维护相应位置。
